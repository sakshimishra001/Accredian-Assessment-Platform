# Security & production configuration

What the platform enforces, and what whoever runs it in production must provide.

## Production configuration (fails closed)

The server validates its environment when it starts (`src/instrumentation.ts` → `src/server/env.ts`).
With `NODE_ENV=production` it refuses to start, naming each missing or unsafe setting (never its
value), unless all of these are set explicitly:

| Setting | Production rule |
| --- | --- |
| `DATABASE_URL` | Required; must not be a test database (name containing "test"). |
| `APP_URL` | Required; `https://`, not localhost. |
| `STORAGE_DRIVER` | Required; `local` (the in-memory driver is for tests only). |
| `STORAGE_LOCAL_DIR` | Required with `local`; an absolute path, outside synced folders. |
| `EMAIL_PROVIDER` | Required; `outbox` (records emails, sends nothing — no email service is connected yet). `test` is refused. |
| `MALWARE_SCANNER` | Required; `none` until a scanning engine is connected (see below). `test` is refused. |
| `TRUST_PROXY` | Required; `true` only behind a reverse proxy that sets `X-Forwarded-For` itself. |

Development and tests keep local defaults (`.env.example` documents every setting).

Development-only commands refuse to run against production: `npm run db:reset`, `npm run db:migrate`
and the seed (also run by `prisma migrate reset`) stop when `NODE_ENV=production` or the database name
doesn't contain "dev", "local" or "test" (`scripts/db-guard.ts`; one-off override:
`ALLOW_DEV_DB_COMMAND=<database name>`). Integration tests refuse `NODE_ENV=production`, any
`TEST_DATABASE_URL` that isn't a test database or equals `DATABASE_URL`, and re-check
`current_database()` before truncating. Production schema changes use `npm run db:deploy` only.

## Staff accounts

- There are no shared or administrator-chosen passwords. An administrator creates the account in
  **Users & Roles** (role: Administrator, Examiner or Doctor / Reviewer) and gets a **one-time link**
  (valid 72 hours) to hand to the person, who sets their own password (at least 12 characters, at most
  72 bytes). Only the link's SHA-256 hash is stored; it works once, and issuing a new link voids the old.
- **Reset password** removes the current password, signs the person out everywhere and issues a new
  one-time link (valid 24 hours).
- **Disable** signs the person out everywhere at once and voids open links; they can't sign in until
  enabled again. Administrators can't disable themselves or the last active administrator.
- First administrator of a new deployment: `npm run staff:create-admin -- --email … --name "…"` prints
  the one-time link in the operator's terminal.
- The development seed (shared `SEED_USER_PASSWORD`) never runs against production (see above).

## Sessions

| | Idle timeout | Maximum length |
| --- | --- | --- |
| Staff | 30 minutes (`STAFF_SESSION_IDLE_MINUTES`) | 12 hours (`STAFF_SESSION_MAX_HOURS`) |
| Learner (exam) | 2 hours (`LEARNER_SESSION_IDLE_MINUTES`) | 12 hours (`LEARNER_SESSION_MAX_HOURS`) |

Every request re-validates the session in PostgreSQL: account active, within both limits and, for
learners, the exam password still active **and usable now** — inside its validity window, inside the
results-only period, or while the learner still has an attempt running. Disabling an account, revoking
a credential or resetting a password ends sessions immediately. In production the cookie is
`__Host-aap_session` (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`).

## Results-only access

After an assessment's results are published, a learner's (non-revoked) exam password signs them in to
that one assessment to see their result for `RESULTS_ACCESS_DAYS` (default 30) days, then it is
expired — for new sign-ins and for open sessions. Results-only access can't start, resume or change an
attempt (the attempt engine checks the assessment window on every write). Revoking the credential ends
it at once.

## Files

- Accepted: PNG/JPEG, PDF, DOCX/XLSX/PPTX, CSV, and plain text/code for learner answers. Content is
  checked against the extension; the browser's MIME type is never trusted.
- **No longer accepted for new uploads** (existing files are still served, as downloads): SVG (can carry
  script) and the legacy binary Office formats .doc/.xls/.ppt (can carry macros and can't be checked).
  Question settings that listed them drop them automatically. Office files containing VBA macros or
  ActiveX controls are refused.
- Downloads: server-decided `Content-Type`, `nosniff`, `Cache-Control: private, no-store`,
  `Cross-Origin-Resource-Policy: same-origin`, framing by this app only; SVG and text open sandboxed,
  SVG always as a download.
- Storage keys are generated by the server and resolved strictly inside the storage folder.
- Removing a question or section deletes its supporting materials' files unless another version of
  the paper still uses them.
- Access: admins — all files; reviewers — materials of papers in review or approved (never drafts or
  learners' answers); examiners — materials of assessments they evaluate and their assigned candidates'
  submitted answers; learners — their exam's materials and their own answers. Anything else is "not found".

### Malware scanning — required before production use

No scanning engine is connected. With `MALWARE_SCANNER=none` every stored file is recorded as
`NOT_SCANNED` (never as clean). Production needs a real engine (e.g. ClamAV via `clamd`, or a cloud
scanning API) implemented as a `MalwareScanner` in `src/server/files/scan.ts` and selected with
`MALWARE_SCANNER`. Infected uploads are then refused before anything is stored, and audited.

## Email

Requests never send email. They record each rendered email in the outbox (`communication_logs`,
`PENDING`) and return; delivery starts right after the response and is completed by the worker:

```bash
npm run outbox:work            # keep polling (OUTBOX_POLL_SECONDS, default 30)
npm run outbox:work -- --once  # one pass (e.g. from cron)
```

Run it alongside the web server in production. Workers claim rows atomically (several can run), a
failure is retried with backoff (1, 2, 4, 8 minutes … up to 5 attempts) and then marked `FAILED`; a row
abandoned by a crashed worker is taken over after 5 minutes. With `EMAIL_PROVIDER=outbox` nothing is
sent and rows end as "Not delivered".

## Audit log

Recorded (never passwords, exam passwords, set-password links or file contents): sign-in success,
failure and throttling; logout; staff account creation, password links issued, passwords set, account
enable/disable; exam credential issue/revoke; assessment publication and status changes; results
publication; evaluation save/finalise/reopen; file upload, removal, deletion, malware rejection and
access; result views (file and result views at most once per user and item every 10 minutes per
server process).

## Known limitations

- `style-src 'unsafe-inline'` in the Content-Security-Policy (inline style attributes in the UI).
- The sign-in throttle and the audit de-duplication are per server process (in memory); several
  instances need a shared store (e.g. Redis) behind the same interfaces.
- Exam sign-in compares the code against up to 5 usable credentials (bcrypt); a single keyed lookup
  would need a new indexed column.
- One-time links are shown to the administrator, who passes them on; once an email provider is
  connected they can be emailed instead.
- No proctoring provider is integrated.
